# Internationalization

**English** | [Bahasa Indonesia](https://github.com/M-Husein/rest-api-laravel-2/wiki/id-Internationalization)

> Status: design contract v1 (2026-10-24). Implemented for the PHP backend and frontend;
> regression tests cover the contract.

Multi-locale support is provided by the optional `locale-switcher` feature package
(`programmeria/laravel-locale-switcher`). The translation runtime is always present; the
feature adds the locale switcher, per-user preference, and localization strategies.

## Scope

- `api`, `api-ui`: single locale.
- `multilingual`, `multilingual-ui`, `site`: multiple locales, locale switcher enabled.
- Public site: localized URLs for SEO.
- Admin area (`/app`): per-user locale, not localized by URL.
- API: locale-aware responses through explicit request signals.

## Terms

- **Default locale**: `config('app.fallback_locale')`, currently `en`.
- **Supported locales**: `config('localizer.supported_locales')`, currently `en` and `id`.
- **Public zone**: localized routes registered through `Route::localize()`, outside `/app`.
- **Admin zone**: `/app` and `/app/*`.
- **API zone**: `/api/*`.
- **Explicit locale signal**: a valid locale in the URL path, `?lang=`, or
  `Accept-Language`.

The locale format is a configured language key (`en`, `id`). Regional variants such as
`en-US` are not supported until they are added to the locale registry.

## Core decisions

1. **Public URL wins.** The public locale is determined only by the URL path. Browser
   headers and the authenticated user's stored language never override it.
2. **Admin user preference wins.** The admin locale comes from `users.lang`. URL and
   query parameters do not localize admin pages.
3. **API explicit signal wins.** For API requests, `?lang` beats `Accept-Language`, which
   beats the authenticated user's `users.lang`, which beats the default locale.
4. **No hidden persistence on the public site.** Public switching changes the URL only.
   Session and cookie locale persistence stay disabled.
5. **Canonical public URLs hide the default locale.** `/en/...` is redirected to the
   unprefixed URL; non-default locales always use a prefix.

## Public URL contract

| Page | `en` (default) | `id` |
|------|----------------|------|
| Home | `/` | `/id` |
| About | `/about` | `/id/about` |
| Articles | `/articles` | `/id/articles` |
| Contact | `/contact-us` | `/id/contact-us` |
| Login | `/login` | `/id/login` |

Rules:

- Default locale is hidden: `/` and `/articles`, not `/en` and `/en/articles`.
- `/en` and `/en/*` redirect to the unprefixed URL. A permanent redirect (301) is
  preferred.
- Non-default locales must have a prefix: `/id`, `/id/articles`.
- An unsupported first segment is not treated as a locale; `/xx/articles` is a 404, not
  a silent fallback.
- `?lang=` is not a public locale signal and must not be generated by public links.
- Query strings and fragments are preserved when switching locale.
- Language switching performs a navigation to the localized URL. A full reload is
  acceptable; no user preference is written.
- Authenticated users on the public site still follow the URL. A user whose stored
  language is `en` can browse `/id` and see Indonesian.
- Auth redirects are outside this contract. Login and register currently redirect to
  `/`; changing that to a localized home is a separate decision.

## Admin contract

- Admin routes live under `/app` and have no locale prefix.
- The locale is `users.lang` when it is supported; otherwise the default locale.
- URL paths and `?lang=` do not change the admin locale.
- Switching language updates the UI immediately, updates the in-memory user, and sends
  `PUT /api/v1/me/language` with `{ "lang": "id" }`.
- The database is the only admin persistence. `localStorage` is not a locale source.
- If the preference request fails, the UI must revert to the previous locale and show
  an error; it must not silently claim success.
- On the next login, the stored `users.lang` is used again.
- Admin pages are private and must not emit public SEO metadata.

## API contract

Locale-aware API responses use this precedence:

1. Valid `?lang=`
2. Valid `Accept-Language`
3. Valid authenticated `users.lang`
4. Default locale

Rules:

- An explicit request signal always beats a stored user preference.
- Invalid values are skipped; resolution continues to the next source.
- The public SPA sends `Accept-Language` equal to the public URL locale. This keeps API
  content aligned with `/id/...` even when the user's stored language differs.
- The admin SPA sends `Accept-Language` equal to `users.lang`.
- `PUT /api/v1/me/language` updates `users.lang` and returns the refreshed user.
- `lang` must be one of the supported locales; invalid values return `422`.
- API error messages and translated payloads follow the resolved request locale.
- `?lang=` on a public page is ignored; it is meaningful only to API consumers.

## Precedence matrix

| Signal | Public page | Admin page | API |
|--------|-------------|------------|-----|
| URL locale prefix | 1 | ignored | ignored |
| `?lang=` | ignored | ignored | 1 |
| `Accept-Language` | ignored | ignored | 2 |
| `users.lang` | ignored | 1 | 3 |
| Default locale | 2 | 2 | 4 |

## Switching behavior

| Zone | UI change | HTTP effect | URL effect | Persistence |
|------|-----------|-------------|------------|-------------|
| Public | Navigate to localized page | None | `/id/...` or unprefixed | None |
| Admin | Update i18n and component locale | `PUT me/language` | Unchanged | `users.lang` |
| API client | Client-managed | Send `?lang` or `Accept-Language` | Not applicable | Optional through `me/language` |

The public and admin zones are intentionally independent. Switching the public site does
not write `users.lang`; switching admin does not change the public URL.

## Frontend strategy contract

The `LocaleStrategy` interface stays the integration point:

| Strategy | `getCurrent` | `apply` | `localizeHref` | `getRouterBasename` |
|----------|--------------|---------|----------------|---------------------|
| `pathname` | URL path | Navigate to localized path | Prefix the path | `''` for default, `/${locale}` otherwise |
| `user` | In-memory user, with startup fallback | Update user cache, PUT preference, change i18n | Identity | `''` |
| `query` | `?lang=` | Update query and navigate | Add `?lang=` | `''` |
| `storage` | Browser storage | Store and change i18n | Identity | `''` |

Rules:

- `zoneStrategy()` selects `APP.strategy`; if absent, it falls back to `/app` path
  detection.
- Public and admin presets use `pathname` and `user` respectively. `query` and `storage`
  remain available for custom integrations but are not enabled by these presets.
- `pathname.getCurrent()` reads only the path. It must not read `localStorage` or the
  authenticated user.
- `pathname.getRouterBasename()` returns `''` for the default locale and `/${locale}`
  for a non-default locale.
- `pathname.localizeHref()` must prefix the pathname. It must not append `?lang=`, must
  not double-prefix, and must preserve query strings and fragments.
- `changeUrlLang()` must remove the prefix when switching to the default locale, add the
  prefix for a non-default locale, and preserve query strings and fragments.
- `user.getCurrent()` reads the in-memory user, not `localStorage`. It falls back to the
  server-injected `window.__APP__.user` before the UI user runtime is registered.
- `user.apply()` updates the in-memory user, calls `PUT me/language`, updates
  `document.documentElement.lang`, and changes i18n.
- `i18nBackend` must send the language being requested, not a stale initial language.
- The core i18n runtime owns `featureApi.getRequestHeaders()` and sends
  `i18n.language` as `Accept-Language`; locale strategies do not own HTTP headers.

## Backend contract

- Public localized routes are registered with `Route::localize()` and use the package's
  `SetLocale` middleware.
- Public config: `hide_default_locale=true`, `redirect_enabled=true`,
  `persist_locale.session=false`, `persist_locale.cookie=false`, `detectors=[]`.
- Empty detectors are intentional: no browser auto-detection on the public site.
- API requests use `SetLang`. Its order must be `?lang` > `Accept-Language` > default,
  with the authenticated user as a fallback only when no explicit signal exists.
- `SetUserLocale` must not override a public URL locale or an explicit API signal. It may
  apply the user preference for admin requests (and for API requests without an explicit
  signal).
- `LanguagePreferenceController` validates `lang` against supported locales and updates
  the authenticated user.
- `/app` and `/api` routes must never be wrapped by `Route::localize()`.

## SEO contract

- Canonical public URLs use the default locale without a prefix.
- Every public page emits `hreflang` links for all supported locales plus `x-default`
  pointing to the default URL.
- `?lang=` URLs are never canonical and must not be indexed.
- Admin pages are private and excluded from public SEO.
- Server-rendered metadata, page translations, and `html lang` follow the resolved public
  locale.
- `locale_directions` stays empty until an RTL locale is added; when added, set `dir`
  accordingly.

Example for `/id/articles`:

- Canonical: `/id/articles`
- Alternate `id`: `/id/articles`
- Alternate `en`: `/articles`
- `x-default`: `/articles`

## Edge cases

- `/en` and `/en/articles` redirect to `/` and `/articles`.
- `/xx` and `/xx/articles` are 404 unless `xx` is added to the locale registry.
- Invalid API `?lang=xx` is skipped; the next valid source is used.
- A user with an unsupported `users.lang` falls back to default; the value is not
  rewritten automatically.
- Removing a locale from config makes its old URLs 404 and makes affected user
  preferences fall back to default.
- Locale switching preserves `?search=...` and `#fragment`.
- Double prefixes such as `/id/id/articles` are never generated and resolve as 404.
- A trailing slash is not part of the canonical URL except for the root path.

## Implementation status

Implemented:

- `LocaleResolver` centralizes valid `?lang` and `Accept-Language` parsing.
- `SetLang` resolves `?lang` before `Accept-Language`, then default.
- `SetUserLocale` skips public URL locales and explicit API signals.
- API token guards apply the user fallback through middleware after authentication.
- Public `/en` URLs canonicalize to unprefixed URLs.
- `pathnameStrategy.localizeHref()` prefixes paths and preserves query/fragment.
- `changeUrlLang()` preserves query/fragment and avoids double prefixes.
- Admin locale reads the in-memory user, not `localStorage`.
- Admin switching reverts and notifies when the preference request fails.
- `i18nBackend` sends the requested language in `Accept-Language`.
- Hreflang links use canonical localized URLs.
- Regression tests: `tests/Feature/LocaleContractTest.php` and
  `tests/frontend/locale.test.ts`.

## Acceptance tests

Backend:

- `GET /` resolves `en`; `GET /id` resolves `id`.
- `GET /en` redirects to `/`; `GET /en/articles` redirects to `/articles`.
- `GET /xx` returns 404.
- An authenticated user with `lang=en` still gets `id` on `/id`.
- `?lang=id` on a public page does not change the public locale.
- `PUT /api/v1/me/language` accepts `id`, rejects `xx`, and returns the updated user.
- API `?lang=id` with `Accept-Language: en` resolves `id`.
- API `Accept-Language: id` without `?lang` resolves `id`.
- API without explicit signal but with `users.lang=id` resolves `id`.
- API without any signal resolves `en`.

Frontend:

- `localizeHref('/articles', 'id')` returns `/id/articles`.
- `localizeHref('/id/articles', 'en')` returns `/articles`.
- `localizeHref('/articles?page=2#top', 'id')` preserves the query and fragment.
- `localizeHref('/id/articles', 'id')` does not double-prefix.
- Public switching changes the URL and does not call `PUT me/language`.
- Admin switching calls `PUT me/language`, updates the UI, and survives reload.
- Admin initial locale comes from the user, not `localStorage`.

SEO:

- `/` and `/id` emit the correct canonical and `hreflang` set.
- `/en` is not canonical.
- Admin pages emit no public canonical or `hreflang`.

## Manual smoke test

Run this before releasing locale changes. Use the `site` preset (or `multilingual-ui`
when there is no public site), built assets, and an admin user whose `users.lang` is `id`.

Public:

- [ ] `/` renders `lang="en"`; `/id` renders `lang="id"`.
- [ ] `/en` and `/en/articles` redirect to `/` and `/articles`.
- [ ] `/xx` and `/xx/articles` return 404.
- [ ] `/id/articles` shows Indonesian content and links; switching to English removes
      the prefix.
- [ ] Switching on `/id/articles?page=2#top` preserves the query and fragment and sends
      no `PUT`.
- [ ] `/reset-password`, `/api/*`, `/app`, `/up`, and `/403` are not prefixed.
- [ ] Login, register, and forgot-password work at `/id/...`.
- [ ] View source: `/` and `/id` have the expected canonical/hreflang; admin has no
      public SEO tags.

Admin:

- [ ] `/app` starts in `users.lang`; changing `localStorage` does not change it.
- [ ] Switching updates the UI immediately and calls `PUT /api/v1/me/language`.
- [ ] The new locale survives a reload and is stored in the database.
- [ ] A failed `PUT` restores the previous locale and shows an error.
- [ ] `/app?lang=en` still uses `users.lang`.

API:

- [ ] A Sanctum token request without `?lang` or `Accept-Language` uses `users.lang`.
- [ ] `?lang` wins over `Accept-Language` and the user preference.
- [ ] `Accept-Language` wins over the user preference.
- [ ] Invalid `?lang` and `Accept-Language` values fall back to the user preference or
      the default locale.
- [ ] Error messages use the resolved request locale.

## Non-goals

- Browser auto-detection on the public site.
- Session or cookie locale persistence.
- Regional locales such as `en-US` or `pt-BR`.
- Translated URL slugs.
- RTL support until an RTL locale is added.
- Server-rendered admin localization.
- Porting this contract to other languages before the PHP behavior is implemented and
  tested.
